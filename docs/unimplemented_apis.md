# Unimplemented MRE APIs

What MREmu does **not** implement, and what it registers but leaves
inert. Generated by [`tools/apisurvey.py`](../tools/apisurvey.py) - do
not edit by hand; run the script instead.

| | Count |
| --- | ---: |
| APIs declared by the SDK | 894 |
| Resolved by `vm_get_sym_entry` | 263 |
| **Unimplemented** (guest gets NULL) | **647** |
| Registered but doing nothing | 29 |
| Registered but partial (hand-maintained) | 13 |
| Implemented | 218 |

## What a missing API does to an app

`vm_get_sym_entry` in [`MREmu/Bridge.cpp`](../MREmu/Bridge.cpp) walks
`func_map` and falls back to `ARModule::vm_get_sym_entry`, which only
resolves symbols the guest binary carries itself. Neither path can find
an unimplemented VM API, so both return **0**:

```cpp
if (ret == 0)
    ret = armodule.vm_get_sym_entry(symbol);   // also returns 0
return ret;                                     // NULL to the guest
```

The app stores that NULL in its dispatch table. A well-written app
checks the pointer and carries on without the feature; one that does
not will jump to address 0. This is why missing entries below are not
automatically fatal - most VXP apps resolve dozens of APIs at start-up
and tolerate a good number being absent.

Note that a *registered* API is not a working one. Several entries are
wired up and then do nothing at all; those are in their own section
below.

## How the survey is derived

- **Declared** - every `vm_*` prototype in the SDK headers under
  `$MRE_SDK/include` (this run: `C:/MRE_SDK/include`).
- **Resolved** - every name in `func_map`, including the
  `FUNCN_FIX` variants, which expose a guest name such as
  `vm_graphic_create_canvas` while the C++ function is
  `vm_graphic_create_canvas_FIX`.
- **Inert** - the resolved name's body was parsed and judged to do no
  work: either empty, or nothing but a `return` of a constant once
  logging calls are discounted.

Two caveats on the method. *Registered* means the symbol resolves, not
that it is correct - a function can be fully implemented and still be
wrong for an app that depends on subtle behaviour. And *declared* comes
from the SDK headers, which are a superset of what any one phone ever
exposed, so a large share of the missing list is hardware no emulator
would have: camera, Bluetooth, telephony, SMS, payment.

The big gaps are whole subsystems rather than scattered holes:
**camera** (36), **video** (19), **editor** (39), **contact** (14),
**MMS** (8), **SMS** (15), **Bluetooth** (33 across three headers),
**payment** (3) and **GPS** (8) are absent end to end. An app that
needs one of these will show the feature as unavailable or simply skip
it, rather than crashing.

MREmu - which then does nothing useful. They are harder to live with
than a missing API, because a missing one can be feature-detected and
these cannot: the app gets a success code or a plausible constant back
and proceeds as though the call worked.

Two kinds, and they are not equally serious. **No behaviour** is an
empty body - the call is a no-op, which is an unambiguous stub.
**Fixed answer** returns a constant; whether that is a defect depends on
what was asked. Answering *what is your character height* with `16` is
correct, and answering *which apps are installed* with `0` is a stub.
The Note column marks which is which.

A one-line body is **not** treated as inert. `vm_graphic_create_layer`
is a single `return create_layer(...)` and is a complete
implementation; only a literal answer is flagged.

The unambiguous stubs - empty bodies, no behaviour at all:

- `vm_audio_resume_bg_play` (MREmu/MREngine/Audio.cpp:254) - Empty body. Counterpart to the suspend stub.
- `vm_audio_suspend_bg_play` (MREmu/MREngine/Audio.cpp:256) - Empty body. Background audio state is not tracked, so an app cannot be suspended this way.
- `vm_graphic_set_font` (MREmu/MREngine/Textout.cpp:144) - No-op. Font selection is not implemented; text is always drawn in the built-in unifont face.
- `vm_input_set_vk_default_enlarge` (MREmu/Bridge.cpp:1661) - Empty bridge lambda.
- `vm_set_app_desired_input_mode` (MREmu/Bridge.cpp:1653) - Empty bridge lambda.
- `vm_start_app_with_para` (MREmu/MREngine/ProgramManager.cpp:35) - does nothing and reports nothing
